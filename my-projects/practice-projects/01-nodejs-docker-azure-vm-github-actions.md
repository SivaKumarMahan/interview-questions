# Practice Project 1: Node.js App to an Azure VM with Docker and GitHub Actions

> This guide walks you through a full CI/CD pipeline that builds a Dockerized Node.js app, pushes it to Docker Hub, and deploys it to an Azure Ubuntu VM over SSH with GitHub Actions.

## Key Concepts

### What you will build

You will build a small Express web app and package it as a Docker image. Every time you push to the `main` branch, GitHub Actions will:

1. Build the Docker image.
2. Push it to Docker Hub with two tags: the commit SHA and `latest`.
3. SSH into an Azure Ubuntu VM.
4. Pull the new image, stop the old container, and start the new one.
5. Call the `/health` endpoint to confirm the new version is up.

Final result: you open `http://<vm-public-ip>/` in a browser and see a JSON response that includes the version (commit SHA) you just pushed. You can also roll back to any older SHA with one click.

### Architecture

```text
 Developer laptop
      |
      | git push (main)
      v
 +--------------------+        docker push         +------------------+
 |  GitHub Actions    | -------------------------> |   Docker Hub     |
 |  (ubuntu-latest)   |   <user>/node-app:<sha>    |  (image registry)|
 |  1. checkout       |   <user>/node-app:latest   +------------------+
 |  2. build image    |                                     |
 |  3. push image     |                                     | docker pull
 |  4. SSH deploy     | ---- SSH (port 22, key) ----+       |
 +--------------------+                             v       v
                                          +-----------------------------+
                                          |  Azure VM (Ubuntu 24.04)    |
                                          |  Docker Engine              |
                                          |  container "node-app"       |
                                          |  host port 80 -> 3000       |
                                          +-----------------------------+
                                                         ^
                                                         | HTTP :80
                                                      End users
```

### Tools and why each one is used

| Tool | What it does here | Why this tool |
| --- | --- | --- |
| Node.js + Express | The sample web app with `/` and `/health` routes | Small, popular, easy to read |
| Docker | Packages the app and its runtime into one image | Same image runs on laptop, CI, and VM |
| Docker Hub | Stores the built images | Free public repos, simple login with an access token |
| GitHub Actions | Runs the build and deploy pipeline on every push | Built into GitHub, no CI server to manage |
| Docker Buildx | Builds the image inside the pipeline | Supports layer caching and multi-platform builds |
| Azure CLI (`az`) | Creates the resource group, VM, and firewall rules | Repeatable, scriptable, no portal clicking |
| Azure VM (Ubuntu) | Runs Docker Engine and the app container | Simple target that teaches the basics of servers |
| SSH (appleboy/ssh-action) | Runs deploy commands on the VM from the pipeline | Simple, widely used, works with a key from a secret |

### Step-by-step

#### Step 1: Create the Express app

Start with a tiny app that has a home route and a health route. The health route is what the pipeline will call after each deploy.

```bash
mkdir node-app && cd node-app
git init
mkdir -p src .github/workflows
```

`package.json`:

```json
{
  "name": "node-app",
  "version": "1.0.0",
  "description": "Sample Express app for CI/CD practice",
  "main": "src/app.js",
  "scripts": {
    "start": "node src/app.js",
    "test": "node --test"
  },
  "engines": {
    "node": ">=24"
  },
  "dependencies": {
    "express": "^5.1.0"
  }
}
```

`src/app.js`:

```javascript
const express = require("express");

const app = express();
const PORT = process.env.PORT || 3000;
const APP_VERSION = process.env.APP_VERSION || "dev";

app.get("/", (req, res) => {
  res.json({
    message: "Hello from Node.js on an Azure VM",
    version: APP_VERSION,
    hostname: require("os").hostname()
  });
});

app.get("/health", (req, res) => {
  res.status(200).json({ status: "ok" });
});

const server = app.listen(PORT, () => {
  console.log(`Server listening on port ${PORT}, version ${APP_VERSION}`);
});

// Graceful shutdown so "docker stop" does not cut requests mid-way
process.on("SIGTERM", () => {
  console.log("SIGTERM received, closing server");
  server.close(() => process.exit(0));
});
```

Generate the lock file and test locally:

```bash
npm install
npm start
# in another terminal
curl http://localhost:3000/health
```

What this does:

- `npm install` creates `package-lock.json`. The Dockerfile uses `npm ci`, which needs this lock file, so commit it.
- `APP_VERSION` is passed in at runtime. We will set it to the Git SHA so you can see which version is live.
- The `SIGTERM` handler lets the app finish open requests when Docker stops the container.

#### Step 2: Write the Dockerfile

Use a small Node LTS base image, install only production dependencies, and run as a non-root user.

`Dockerfile`:

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-alpine

ENV NODE_ENV=production
WORKDIR /app

# Copy only dependency files first so this layer is cached
COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force

# Copy the app source, owned by the non-root "node" user
COPY --chown=node:node src ./src

# The official node image already has a "node" user (uid 1000)
USER node

EXPOSE 3000

HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD wget -qO- http://localhost:3000/health || exit 1

CMD ["node", "src/app.js"]
```

What this does:

- `node:24-alpine` is a small LTS image. You can use `node:24-slim` (Debian based) if a dependency needs glibc.
- Copying `package*.json` before the source means a code change does not reinstall all packages. Docker reuses the cached `npm ci` layer.
- `npm ci --omit=dev` installs exact versions from the lock file and skips dev dependencies.
- `USER node` runs the process as a non-root user. If the app is hacked, the attacker is not root inside the container.
- `HEALTHCHECK` lets Docker mark the container as `healthy` or `unhealthy`. Alpine includes `wget` through BusyBox.
- `CMD ["node", ...]` in exec form makes Node PID 1, so it receives `SIGTERM` directly.

#### Step 3: Add a .dockerignore

This keeps the build context small and stops secrets or local files from going into the image.

`.dockerignore`:

```text
node_modules
npm-debug.log
.git
.github
.gitignore
.env
*.md
Dockerfile
.dockerignore
coverage
```

What this does:

- `node_modules` is excluded because the image installs its own clean copy.
- `.env` and `.git` are excluded so secrets and history never land in an image layer.

Build and run it locally:

```bash
docker build -t node-app:local .
docker run -d --name node-app-local -p 8080:3000 -e APP_VERSION=local node-app:local
curl http://localhost:8080/
docker ps   # STATUS should show (healthy) after ~10-30 seconds
docker rm -f node-app-local
```

#### Step 4: Create the Azure VM with the Azure CLI

Create a resource group and an Ubuntu VM with SSH key login. Using the CLI makes the setup repeatable.

```bash
# Variables (change to your values)
RG="<resource-group>"            # for example rg-node-app-lab
LOCATION="eastus"
VM_NAME="vm-node-app"
ADMIN_USER="azureuser"

az group create --name "$RG" --location "$LOCATION"

az vm create \
  --resource-group "$RG" \
  --name "$VM_NAME" \
  --image Ubuntu2404 \
  --size Standard_B2s \
  --admin-username "$ADMIN_USER" \
  --generate-ssh-keys \
  --public-ip-sku Standard \
  --output table
```

What this does:

- `--image Ubuntu2404` is an alias for Ubuntu Server 24.04 LTS. If your CLI is old and does not know the alias, use the full URN `Canonical:ubuntu-24_04-lts:server:latest`, or run `az vm image list --output table` to see aliases.
- `--generate-ssh-keys` uses `~/.ssh/id_rsa.pub` if it exists, or creates a new key pair. Password login is disabled by default for Linux VMs created with SSH keys.
- The command also creates a VNet, subnet, public IP, NIC, and a Network Security Group (NSG) named `<vm-name>NSG` with an SSH rule named `default-allow-ssh`.

Get the public IP:

```bash
VM_IP=$(az vm show -d -g "$RG" -n "$VM_NAME" --query publicIps -o tsv)
echo "$VM_IP"
```

#### Step 5: Open port 80 and restrict SSH

The app must be reachable on port 80. SSH (port 22) should not be open to the whole internet.

```bash
# Open HTTP
az vm open-port --resource-group "$RG" --name "$VM_NAME" --port 80 --priority 900

# Restrict SSH to your own public IP
MY_IP=$(curl -s https://api.ipify.org)
az network nsg rule update \
  --resource-group "$RG" \
  --nsg-name "${VM_NAME}NSG" \
  --name default-allow-ssh \
  --source-address-prefixes "${MY_IP}/32"
```

What this does:

- `az vm open-port` adds an inbound NSG rule that allows TCP 80 from any source. `--priority` must be unique within the NSG.
- `az network nsg rule update` changes the SSH rule so only your IP can connect.

Important trade-off: GitHub-hosted runners use changing IP addresses. If SSH only allows your IP, the pipeline cannot connect. For this lab you have three options:

1. Keep port 22 open but key-only (no passwords). Simple, acceptable for a short lab.
2. In the workflow, log in to Azure with OIDC and add the runner IP to the NSG at the start, then remove it at the end.
3. Better for real use: a self-hosted runner inside the VNet, Azure Bastion, or a pull-based deploy (the VM pulls new images itself). See Next improvements.

#### Step 6: Install Docker on the VM

SSH into the VM and install Docker Engine from Docker's official apt repository.

```bash
ssh azureuser@"$VM_IP"
```

On the VM:

```bash
# Remove old or conflicting packages (safe if none are installed)
for pkg in docker.io docker-doc docker-compose podman-docker containerd runc; do
  sudo apt-get remove -y "$pkg" 2>/dev/null || true
done

# Add Docker's official GPG key and repo
sudo apt-get update
sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# Start Docker on boot
sudo systemctl enable --now docker

# Let the admin user run docker without sudo
sudo usermod -aG docker "$USER"
exit
```

Reconnect and check:

```bash
ssh azureuser@"$VM_IP" "docker version && docker run --rm hello-world"
```

What this does:

- Installs Docker from Docker's repo, which is newer than Ubuntu's `docker.io` package.
- `usermod -aG docker` lets the deploy user run `docker` without `sudo`. You must log out and back in for the group change to apply.
- A quicker lab option is `curl -fsSL https://get.docker.com | sudo sh`. Docker does not recommend the convenience script for production, so the apt steps are shown here.

Security note: members of the `docker` group effectively have root on the host. Only add trusted users.

#### Step 7: Create a deploy SSH key for GitHub Actions

Do not reuse your personal SSH key in CI. Create a dedicated key just for deployments.

```bash
# On your laptop
ssh-keygen -t ed25519 -C "github-actions-deploy" -f ./gh_deploy_key -N ""

# Add the public key to the VM's authorized_keys
ssh-copy-id -i ./gh_deploy_key.pub azureuser@"$VM_IP"

# Test it
ssh -i ./gh_deploy_key azureuser@"$VM_IP" "echo deploy key works"
```

What this does:

- `-N ""` creates the key without a passphrase so the pipeline can use it.
- The private key (`gh_deploy_key`) goes into a GitHub secret. Delete the local copy after saving it, or store it in a password manager.
- You can revoke it at any time by removing its line from `~/.ssh/authorized_keys` on the VM.

#### Step 8: Create a Docker Hub access token

Never put your Docker Hub password in CI. Use an access token with limited scope.

1. Log in to Docker Hub.
2. Go to Account settings, then Personal access tokens.
3. Create a token named `github-actions` with Read and Write access.
4. Copy the token (you only see it once).
5. Create a repository `node-app` in Docker Hub (public is fine for this lab).

#### Step 9: Add GitHub secrets and variables

Go to your repo, then Settings, then Secrets and variables, then Actions.

| Name | Type | Value |
| --- | --- | --- |
| `DOCKERHUB_USERNAME` | Variable or secret | `<your-dockerhub-username>` |
| `DOCKERHUB_TOKEN` | Secret | The Docker Hub access token |
| `VM_HOST` | Secret | The VM public IP or DNS name |
| `VM_USER` | Secret | `azureuser` |
| `VM_SSH_KEY` | Secret | Full contents of `gh_deploy_key` (private key, including BEGIN/END lines) |

Optional but recommended: create a GitHub Environment named `production` (Settings, then Environments). You can add required reviewers so a human approves each deploy.

You can also set secrets from the terminal with the GitHub CLI:

```bash
gh secret set DOCKERHUB_TOKEN
gh secret set VM_HOST --body "$VM_IP"
gh secret set VM_USER --body "azureuser"
gh secret set VM_SSH_KEY < ./gh_deploy_key
gh variable set DOCKERHUB_USERNAME --body "<your-dockerhub-username>"
```

#### Step 10: Write the deploy workflow

This workflow has two jobs: `build` (build and push the image) and `deploy` (SSH to the VM and swap the container).

`.github/workflows/deploy.yml`:

```yaml
name: Build and Deploy

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: deploy-production
  cancel-in-progress: false

env:
  IMAGE_NAME: ${{ vars.DOCKERHUB_USERNAME }}/node-app

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      image_tag: ${{ steps.vars.outputs.tag }}
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set image tag
        id: vars
        run: echo "tag=${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"

      - name: Log in to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ vars.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Build and push image
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: |
            ${{ env.IMAGE_NAME }}:${{ steps.vars.outputs.tag }}
            ${{ env.IMAGE_NAME }}:latest
          cache-from: type=gha
          cache-to: type=gha,mode=max

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Deploy to Azure VM over SSH
        uses: appleboy/ssh-action@v1.0.3
        env:
          IMAGE: ${{ env.IMAGE_NAME }}:${{ needs.build.outputs.image_tag }}
          TAG: ${{ needs.build.outputs.image_tag }}
        with:
          host: ${{ secrets.VM_HOST }}
          username: ${{ secrets.VM_USER }}
          key: ${{ secrets.VM_SSH_KEY }}
          port: 22
          envs: IMAGE,TAG
          script_stop: true
          script: |
            echo "Deploying $IMAGE"
            docker pull "$IMAGE"
            docker stop node-app || true
            docker rm node-app || true
            docker run -d \
              --name node-app \
              --restart unless-stopped \
              -p 80:3000 \
              -e APP_VERSION="$TAG" \
              "$IMAGE"
            # Wait for the app to become healthy (max ~30s)
            for i in $(seq 1 10); do
              if curl -fsS http://localhost/health; then
                echo " - health check passed"
                break
              fi
              if [ "$i" -eq 10 ]; then
                echo "Health check failed"
                docker logs --tail 50 node-app
                exit 1
              fi
              sleep 3
            done
            # Remove old unused images to save disk
            docker image prune -af --filter "until=168h"

      - name: External health check
        run: |
          for i in $(seq 1 10); do
            if curl -fsS "http://${{ secrets.VM_HOST }}/health"; then
              echo " - site is reachable from the internet"
              exit 0
            fi
            sleep 3
          done
          echo "External health check failed"
          exit 1
```

What this does:

- `on: push: branches: [main]` runs the pipeline on every push to `main`. `workflow_dispatch` adds a manual "Run workflow" button.
- `permissions: contents: read` gives the `GITHUB_TOKEN` the minimum rights it needs.
- `concurrency` stops two deploys from running at the same time and fighting over the container.
- `${GITHUB_SHA::7}` makes a short SHA tag such as `a1b2c3d`. The SHA tag is immutable and is what we deploy. `latest` is only a convenience.
- `docker/login-action@v3` logs in with the token, not your password.
- `docker/build-push-action@v6` builds and pushes both tags. `cache-from/cache-to: type=gha` stores layer cache in GitHub Actions cache so builds are faster.
- `outputs.image_tag` passes the tag from the `build` job to the `deploy` job.
- `environment: production` lets you add manual approval and environment-specific secrets.
- `appleboy/ssh-action@v1.0.3` is pinned to a version. For stronger supply-chain safety you can pin to a full commit SHA.
- `envs: IMAGE,TAG` forwards these environment variables to the remote script.
- `script_stop: true` stops the remote script at the first failing command. (In newer major versions of this action the input name changed; check the README if you upgrade.)
- `docker stop ... || true` does not fail on the first deploy, when no container exists yet.
- `--restart unless-stopped` makes Docker restart the container after a crash or VM reboot, unless you stopped it on purpose.
- `-p 80:3000` maps VM port 80 to the app port 3000 inside the container. The app runs as non-root, so it cannot bind port 80 itself, which is why we map.
- The health loop fails the job if the new container does not answer, and prints logs to help you debug.

Alternative without a third-party action (plain SSH):

```yaml
      - name: Deploy with plain ssh
        env:
          IMAGE: ${{ env.IMAGE_NAME }}:${{ needs.build.outputs.image_tag }}
        run: |
          mkdir -p ~/.ssh
          echo "${{ secrets.VM_SSH_KEY }}" > ~/.ssh/deploy_key
          chmod 600 ~/.ssh/deploy_key
          ssh-keyscan -H "${{ secrets.VM_HOST }}" >> ~/.ssh/known_hosts
          ssh -i ~/.ssh/deploy_key "${{ secrets.VM_USER }}@${{ secrets.VM_HOST }}" \
            "docker pull $IMAGE && \
             (docker rm -f node-app || true) && \
             docker run -d --name node-app --restart unless-stopped -p 80:3000 $IMAGE"
```

Note: `ssh-keyscan` trusts whatever key the host shows at that moment. For stronger security, save the VM's host key in a secret and write it to `known_hosts` instead.

#### Step 11: Add a rollback workflow

Because every image has an immutable SHA tag, rollback is just "deploy an older tag". This workflow lets you type a tag and redeploy it.

`.github/workflows/rollback.yml`:

```yaml
name: Rollback

on:
  workflow_dispatch:
    inputs:
      image_tag:
        description: "Image tag (short SHA) to redeploy, for example a1b2c3d"
        required: true
        type: string

permissions:
  contents: read

concurrency:
  group: deploy-production
  cancel-in-progress: false

jobs:
  rollback:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Redeploy previous image
        uses: appleboy/ssh-action@v1.0.3
        env:
          IMAGE: ${{ vars.DOCKERHUB_USERNAME }}/node-app:${{ inputs.image_tag }}
          TAG: ${{ inputs.image_tag }}
        with:
          host: ${{ secrets.VM_HOST }}
          username: ${{ secrets.VM_USER }}
          key: ${{ secrets.VM_SSH_KEY }}
          envs: IMAGE,TAG
          script_stop: true
          script: |
            docker pull "$IMAGE"
            docker rm -f node-app || true
            docker run -d --name node-app --restart unless-stopped \
              -p 80:3000 -e APP_VERSION="$TAG" "$IMAGE"
            sleep 5
            curl -fsS http://localhost/health
```

What this does:

- `workflow_dispatch` with an input shows a text box in the Actions tab.
- It reuses the same `concurrency` group so a rollback and a deploy never overlap.
- To find old tags, look at the Docker Hub repo tags page or the Git log (`git log --oneline`).

Manual rollback from your laptop, if GitHub is down:

```bash
ssh azureuser@"$VM_IP" '
  docker pull <your-dockerhub-username>/node-app:<old-sha> &&
  docker rm -f node-app &&
  docker run -d --name node-app --restart unless-stopped -p 80:3000 \
    -e APP_VERSION=<old-sha> <your-dockerhub-username>/node-app:<old-sha>'
```

### Common problems and fixes

| Problem | Likely cause | Fix |
| --- | --- | --- |
| `docker/login-action` fails with `unauthorized` | Wrong username or expired/revoked token | Recreate the Docker Hub token and update `DOCKERHUB_TOKEN`; check `DOCKERHUB_USERNAME` |
| `npm ci` fails in the Docker build | `package-lock.json` missing or out of sync | Run `npm install` locally and commit `package-lock.json` |
| SSH step: `dial tcp ... i/o timeout` | NSG blocks port 22 from the runner IP | Allow the runner (see Step 5 options) or use a self-hosted runner |
| SSH step: `ssh: handshake failed: unable to authenticate` | Public key not on VM, or private key pasted wrong | Re-run `ssh-copy-id`; paste the full private key including BEGIN/END lines |
| `permission denied while trying to connect to the Docker daemon socket` | Deploy user not in `docker` group | `sudo usermod -aG docker azureuser`, then reconnect |
| `Bind for 0.0.0.0:80 failed: port is already allocated` | Old container or another service (nginx) uses port 80 | `docker ps -a`, remove the old container; stop the other service |
| Browser cannot reach the site but `curl localhost` works on VM | Port 80 not open in NSG | `az vm open-port --port 80 ...` |
| Container keeps restarting | App crashes on start | `docker logs node-app`; check env vars and that `CMD` path is correct |
| `toomanyrequests` on pull | Docker Hub pull rate limit | Log in on the VM with `docker login`, or use a private registry such as ACR |
| VM disk fills up | Old images pile up | `docker image prune -af` (already in the script) |

### Clean up

Deleting the resource group deletes the VM, disk, public IP, NSG, and VNet in one command.

```bash
az group delete --name "<resource-group>" --yes --no-wait

# Confirm it is gone (may take a few minutes)
az group exists --name "<resource-group>"
```

Also:

- Revoke the Docker Hub access token in Docker Hub settings.
- Delete the GitHub secrets, or the whole repo if it was only for practice.
- Remove the local deploy key: `rm -f ./gh_deploy_key ./gh_deploy_key.pub`.

### Next improvements

- Remove SSH from the internet: use a self-hosted runner in the same VNet, Azure Bastion, or a pull-based agent (for example Watchtower or a systemd timer) so no inbound port 22 is needed.
- Use Azure Container Registry with a managed identity on the VM instead of Docker Hub credentials.
- Add a test job (`npm test`, lint) and an image scan (Trivy or Docker Scout) before push; fail on critical CVEs.
- Put Nginx or Caddy in front for HTTPS with Let's Encrypt.
- Zero-downtime deploys: run the new container on another port, health check it, then switch the reverse proxy (blue-green).
- Create the VM with Terraform or Bicep and install Docker with cloud-init (`--custom-data`) instead of manual SSH.
- Send container logs to Azure Monitor and add an availability test on `/health`.
- Pin actions to full commit SHAs and enable Dependabot for GitHub Actions.

### How to explain this project in an interview

> "As a hands-on practice project, I built an end-to-end CI/CD pipeline for a small Node.js Express app. I containerized it with a Dockerfile that uses a Node LTS Alpine image, installs only production dependencies with npm ci, and runs as a non-root user. On every push to main, a GitHub Actions workflow builds the image with Buildx, tags it with the commit SHA and latest, and pushes it to Docker Hub using an access token stored as a secret. A second job SSHes into an Azure Ubuntu VM that I created with the Azure CLI, pulls the SHA-tagged image, replaces the running container, and runs a health check against the /health endpoint. If the check fails, the job fails and prints container logs. Because every image has an immutable SHA tag, rollback is just a manual workflow that redeploys an older tag. If I took it further, I would remove public SSH by using a self-hosted runner or pull-based deploy, and add HTTPS and image scanning."

Points that impress interviewers:

- You deploy the immutable SHA tag, not `latest`, and you can explain why that makes rollback safe.
- You thought about security: non-root container, access token instead of password, dedicated deploy key, restricted NSG, least-privilege `permissions`.
- You verify deploys with a health check and fail the pipeline if it does not pass.
- You can name the limits (single VM, brief downtime during swap, SSH exposure) and how to fix them.

## Interview Questions

<details><summary>Q1. [Basic] Why do you tag the image with the commit SHA and not only with <code>latest</code>?</summary>

**Answer:**

`latest` is a moving tag. It points to whatever was pushed last, so you cannot tell which code is running, and two servers pulling `latest` at different times may run different code.

A SHA tag is unique and immutable in practice. It links the running container to an exact commit. This gives you:

- Traceability: you can see exactly what is deployed.
- Safe rollback: redeploy the previous SHA tag.
- Reproducibility: the same tag always gives the same image.

We still push `latest` as a convenience for local testing, but the pipeline deploys the SHA tag.

</details>

<details><summary>Q2. [Basic] What does <code>--restart unless-stopped</code> do and how is it different from <code>always</code>?</summary>

**Answer:**

It tells the Docker daemon to restart the container if it exits or if the Docker daemon or VM restarts.

- `always`: restarts the container even if you stopped it manually, once the daemon restarts.
- `unless-stopped`: same, but if you ran `docker stop`, it stays stopped after a daemon restart.
- `on-failure[:N]`: restarts only on a non-zero exit code, optionally up to N times.
- `no`: default, never restarts.

`unless-stopped` is a good default for a single-host app because it survives reboots but respects manual stops during maintenance.

</details>

<details><summary>Q3. [Basic] Why does the Dockerfile copy <code>package.json</code> and <code>package-lock.json</code> before the source code?</summary>

**Answer:**

Docker caches each layer. If the files copied in a step have not changed, Docker reuses the cached layer and all steps after it until something changes.

Dependencies change rarely, source code changes often. By copying only the package files first and running `npm ci`, the slow install step is cached. A code-only change rebuilds just the final `COPY src` layer, which takes seconds.

If you copied everything first, any code change would invalidate the cache and reinstall all packages every build.

</details>

<details><summary>Q4. [Intermediate] How do you store and use secrets in this pipeline, and what would you improve?</summary>

**Answer:**

Current approach:

- Docker Hub access token (not the password) stored as `DOCKERHUB_TOKEN` GitHub secret.
- A dedicated, revocable ed25519 deploy key stored as `VM_SSH_KEY`.
- Secrets live in a GitHub Environment (`production`) with optional required reviewers.
- `permissions: contents: read` limits the workflow token.

GitHub masks secrets in logs, and secrets are not passed to workflows triggered from forks.

Improvements:

- Use Azure Container Registry and give the VM a managed identity with `AcrPull`, so no registry password is stored on the VM.
- Use OIDC (`azure/login` with federated credentials) for any Azure API calls, so there is no long-lived Azure secret.
- Remove the need for an SSH key altogether with a self-hosted runner or a pull-based deploy.
- Rotate tokens on a schedule and pin actions to commit SHAs.

</details>

<details><summary>Q5. [Intermediate] The deploy job fails with an SSH timeout, but you can SSH from your laptop. What is wrong? <em>(scenario)</em></summary>

**Answer:**

Most likely the NSG only allows port 22 from your own IP. GitHub-hosted runners use changing public IPs from a large range, so their connection is dropped and times out.

How to confirm: check the NSG rule:

```bash
az network nsg rule show -g <resource-group> --nsg-name <vm-name>NSG -n default-allow-ssh \
  --query sourceAddressPrefixes
```

Fixes, from quick to best:

1. For a lab, allow 22 from any source but keep key-only auth.
2. In the workflow, log in with OIDC, get the runner IP (`curl https://api.ipify.org`), add a temporary NSG rule, deploy, then delete the rule in an `if: always()` step.
3. Use a self-hosted runner inside the VNet so SSH stays private.
4. Switch to a pull-based deploy so no inbound SSH is needed.

</details>

<details><summary>Q6. [Intermediate] The pipeline is green but users still see the old version. How do you troubleshoot? <em>(scenario)</em></summary>

**Answer:**

Check step by step:

1. Did the image push the new tag? Check Docker Hub tags for the new SHA.
2. What is running on the VM? `docker ps` and `docker inspect node-app --format '{{.Config.Image}}'`. Compare with the expected SHA.
3. Did the deploy pull `latest` from a cache? If the script used `latest` without `docker pull`, Docker reuses the local image. Deploying the SHA tag avoids this.
4. Is another container or process still serving port 80? `sudo ss -ltnp | grep :80`.
5. Is there a cache in front (browser, CDN, proxy)? Try `curl` with a cache-busting query string.
6. Is DNS pointing to a different VM? `nslookup` the domain and compare with the VM IP.

The `/` route returns `APP_VERSION`, so `curl http://<vm-ip>/` quickly shows which SHA is live.

</details>

<details><summary>Q7. [Intermediate] Why run the container as a non-root user, and how does port 80 still work?</summary>

**Answer:**

By default, processes in a container run as root (uid 0). If an attacker exploits the app, root inside the container makes container escape and host damage easier. Running as a non-root user (`USER node`) reduces the blast radius.

A non-root process cannot bind ports below 1024 by default, so the app listens on 3000 inside the container. Docker maps host port 80 to container port 3000 with `-p 80:3000`. The port mapping is done by Docker on the host, not by the app, so the app never needs root.

</details>

<details><summary>Q8. [Advanced] This deploy has a few seconds of downtime. How would you make it zero-downtime on a single VM? <em>(scenario)</em></summary>

**Answer:**

The downtime happens between `docker rm` of the old container and the new one being ready.

A blue-green approach on one VM:

1. Put a reverse proxy (Nginx, Caddy, or Traefik) on port 80.
2. Run the current version as `node-app-blue` on, for example, port 3001.
3. Deploy the new version as `node-app-green` on port 3002.
4. Health check `http://localhost:3002/health` until it passes.
5. Switch the proxy upstream to 3002 and reload it (reload is graceful, no dropped connections).
6. Stop the blue container after in-flight requests finish.

Traefik with Docker labels can do this automatically. The graceful `SIGTERM` handler in the app also helps by letting open requests finish.

For real high availability you need at least two VMs behind a load balancer (VM Scale Set plus Azure Load Balancer or Application Gateway), or a platform like App Service slots or AKS rolling updates.

</details>

<details><summary>Q9. [Advanced] How would you remove the need for inbound SSH from GitHub Actions entirely?</summary>

**Answer:**

Options:

- Self-hosted runner on the VM or in the same VNet: the runner makes an outbound HTTPS connection to GitHub and picks up jobs. Jobs run locally, so no inbound port is needed. Use it only for private repos, because untrusted code from forks could run on it.
- Pull-based deploy: the VM checks the registry for a new tag (Watchtower, or a small systemd timer script) and updates itself. CI only pushes the image.
- Azure Run Command: `az vm run-command invoke` runs a script on the VM through the Azure control plane. Combine it with OIDC login so no SSH key and no open port 22.
- Azure Bastion for human access instead of a public SSH port.

`az vm run-command` with OIDC is a neat fit here because it reuses Azure RBAC for authorization and is fully audited in the Activity Log.

</details>

<details><summary>Q10. [Advanced] When would you stop using a single VM with Docker for this app, and what would you move to?</summary>

**Answer:**

A single VM is fine for labs, demos, and small internal tools. Move on when you need:

- High availability: one VM is a single point of failure.
- Autoscaling: traffic changes a lot.
- Less patching: you do not want to manage OS updates, Docker upgrades, and disks.
- Many services: you need service discovery, rolling updates, and secrets management.

Choices on Azure:

- Azure App Service for Containers or Azure Container Apps: managed, autoscaling, built-in HTTPS, deployment slots or revisions. Best next step for one web app.
- Azure Container Instances: quick single containers or jobs, but no autoscaling.
- AKS: many microservices, advanced networking, and a team that can run Kubernetes.

The pipeline barely changes: build, push, then call the platform's deploy command instead of SSH.

</details>
