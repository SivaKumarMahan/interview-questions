Q: Automating Docker Installation & Configuration using Ansible?

1. This playbook:
a. Installs Docker and dependencies.
b. Adds the official Docker repository.
c. Starts and enables the Docker service.
d. Verifies installation with a simple check.

```yaml
---
- name: Install and Configure Docker
  hosts: all
  become: yes

    tasks:
        - name: Install required packages
        apt:
            name:
            - apt-transport-https
            - ca-certificates
            - curl
            - gnupg
            - software-properties-common
            - lsb-release
            state: present
            update_cache: yes
    
        - name: Add Docker GPG key
        apt_key:
            url: https://download.docker.com/linux/ubuntu/gpg
            state: present
    
        - name: Add Docker repository
        apt_repository:
            repo: deb [arch=amd64] https://download.docker.com/linux/ubuntu {{ ansible_distribution_release }} stable
            state: present
    
        - name: Install Docker Engine
        apt:
            name: docker-ce
            state: latest
            update_cache: yes
    
        - name: Start and enable Docker service
        systemd:
            name: docker
            state: started
            enabled: yes
    
        - name: Verify Docker installation
        command: docker --version
        register: docker_version
    
        - name: Display Docker version
        debug:
            msg: "Docker installed successfully: {{ docker_version.stdout }}"
``` 

## Save the playbook as docker_install.yml
This playbook can be executed on any Ubuntu-based system to automate the installation and configuration of Docker. Make sure to run it with appropriate privileges (e.g., using `ansible-playbook -K` to prompt for the sudo password).

2. Update your inventory file: hosts.ini
```ini
[all]
server1 ansible_host=192.168.1.10 ansible_user=ubuntu ansible_ssh_private_key_file=~/.ssh/id_rsa
server2 ansible_host=192.168.1.11 ansible_user=ubuntu ansible_ssh_private_key_file=~/.ssh/id_rsa
server3 ansible_host=192.168.1.12 ansible_user=ubuntu ansible_ssh_private_key_file=~/.ssh/id_rsa

# Note: Replace the IP addresses and user details with your actual server information.

#Optinally define groups if you want to target specific servers
[webservers]
server1
server2
[dbservers]
server3
``` 

3. Run the playbook:
```bash
ansible-playbook -i hosts.ini docker_install.yml
```

As a DevOps engineer, we all use Nginx for one or another purpose.

But most don’t understand how powerful Nginx really is.

Here’s what happens when a request hits your Nginx server:

Nginx sits as your system’s entry point, listening on ports 80 and 443. When a request comes in, it instantly decides the best action based on your configuration.

- For static files like images or CSS, Nginx serves them directly from disk. Blazing fast with no backend needed.

- For dynamic requests, it acts as a reverse proxy. It forwards requests to your backend applications and waits for responses.

👉But here’s where it gets powerful:

- Load balancing across multiple backend servers with different strategies.
- TLS termination handling all SSL certificates and encryption.
- Response caching to serve repeated requests instantly.
- Rate limiting and IP blocking for security.
- Response compression to reduce bandwidth.
- Custom headers for CORS and security policies.

All of this is controlled by a single nginx.conf file. It reloads without downtime.

👉In Kubernetes environments, Nginx serves as an Ingress Controller. It manages and routes traffic to internal services based on paths and rules.

✅That’s why Nginx powers over 400 million websites. It’s not just a web server - it’s a complete traffic management solution.

1. Scenario:
A user cannot access a website, but you can ping the IP address of the server.
 👉 What could be the issue?
✅ Answer:
DNS resolution issue. The domain name is not translating to the IP.
Troubleshoot with nslookup or dig to verify DNS.
Check if DNS server is configured correctly in client machine.

2. Scenario:
Two hosts are in the same subnet, but they cannot ping each other.
 👉 How do you troubleshoot?
✅ Answer:
Check if both hosts have correct IP & subnet mask.
Verify ARP table – use arp -a.
Ensure no firewall/ACL blocking ICMP.
Check switch port status (show interface in Cisco).
Possible VLAN mismatch between the two hosts.

3. Scenario:
You configured a static route on a router, but traffic is not flowing.
 👉 What could be wrong?
✅ Answer:
Check if next-hop IP is reachable.
Ensure exit interface is up.
Verify if there’s a more specific route in the routing table overriding it.
Confirm no ACL is blocking traffic.

4. Scenario:
A server is accessible from the same LAN but not from outside network.
 👉 What do you check?
✅ Answer:
Check if the default gateway is configured on server.
Verify NAT or firewall rules on the router.
Ensure routing is configured properly to reach external network.
Check public IP mapping if it’s cloud/on-prem.

5. Scenario:
Your company’s web application is slow. How would you identify if it’s a network issue or server issue?
✅ Answer:
Use ping & traceroute to check latency/packet loss.
Check bandwidth utilization on network devices.
Use Wireshark/TCPdump to analyze traffic.
If network looks fine, check server performance (CPU, memory, application logs).

6. Scenario:
One site of your company is down, but all other sites are working fine.
 👉 How do you approach?
✅ Answer:
Check physical connectivity (fiber, link down, interface down).
Verify WAN link status with ISP.
Run routing checks (OSPF, BGP, static routes).
Use failover/backups if HA is configured.

7. Scenario:
You see duplicate IP addresses in your network.
 👉 How do you resolve?
✅ Answer:
Use arp -a to identify MAC addresses.
Locate devices with conflicting IP.
Assign unique IP addresses or enable DHCP snooping / IP conflict detection.
Document IP allocation properly.

What is a dynamically typed language?

Before we understand a dynamically typed language, we should learn about what typing is. Typing refers to type-checking in programming languages. In a strongly-typed language, such as Python, "1" + 2 will result in a type error since these languages don't allow for "type-coercion" (implicit conversion of data types). On the other hand, a weakly-typed language, such as Javascript, will simply output "12" as result.

Type-checking can be done at two stages -

Static - Data Types are checked before execution.
Dynamic - Data Types are checked during execution.

1️⃣ Scaling:
--> Manual Scaling: You can scale a Deployment by changing the replicas field in the deployment.yaml file or using kubectl scale.
 Example:

kubectl scale deployment myapp --replicas=5

This increases or decreases the number of pods running for the application.
--> Automatic Scaling (Horizontal Pod Autoscaler - HPA):
 Kubernetes can automatically scale pods based on CPU, memory, or custom metrics.
 Example:

kubectl autoscale deployment myapp --cpu-percent=50 --min=2 --max=10

This keeps the application responsive under varying load.

2️⃣ Rolling Updates:
--> Kubernetes allows updating applications without downtime.
--> When you update the image version in your Deployment (image: myapp:v2), Kubernetes gradually replaces old pods with new ones.
You can monitor rollout:

kubectl rollout status deployment/myapp

If something goes wrong, you can rollback:

kubectl rollout undo deployment/myapp

3️⃣ Self-Healing:
--> Kubernetes automatically restarts failed pods and replaces them if a node goes down.
--> This ensures the desired number of replicas is always running, improving reliability.

💡 Interview Tip
If asked:
“How does Kubernetes ensure zero downtime during updates?”
You can answer:
“Kubernetes performs rolling updates, gradually replacing old pods with new ones while keeping the required number of pods available, ensuring zero downtime. If an update fails, it can automatically rollback to the previous stable version.”

Question: How Jenkins automates deployment to Kubernetes?
Answer: Automatically deploy your application to Kubernetes whenever new code is pushed to GitHub.

🧩 Step-by-Step Process:
Step 1: Developer pushes code to GitHub
Developer commits new code.
The push triggers a Jenkins Pipeline via webhook.
🔹 Example:
 You configure a GitHub → Jenkins webhook (under repo settings → webhooks).

Step 2: Jenkins pipeline starts (Jenkinsfile)
The Jenkinsfile defines all stages for CI/CD:
Clone Code
Build Docker Image
Push to Artifact Registry (GCP, ECR, or Docker Hub)
Deploy to Kubernetes Cluster

Step 3: Jenkins builds the Docker image

stage('Build Docker Image') {
 steps {
 script {
 sh 'docker build -t https://lnkd.in/ghadMb5B .'
 }
 }
}

Step 4: Push the Docker image to registry

stage('Push Image to Registry') {
 steps {
 script {
 sh 'docker push https://lnkd.in/ghadMb5B'
 }
 }
}
🔐 Jenkins uses credentials plugin to securely store Docker Hub or GCP service account credentials.

Step 5: Deploy to Kubernetes
You can either:
Use kubectl directly from Jenkins, or
Use Helm for production-grade deployment.
Example (kubectl):

stage('Deploy to Kubernetes') {
 steps {
 script {
 sh 'kubectl set image deployment/myapp myapp=https://lnkd.in/ghadMb5B --record'
 }
 }
}
This command updates your Kubernetes deployment with the new image version.

Step 6: Verify and monitor deployment
Jenkins can also run health checks:

stage('Verify Deployment') {
 steps {
 sh 'kubectl rollout status deployment/myapp'
 }
}
If deployment fails, Jenkins can roll back or alert you via email/Slack.

✅ Summary of CI/CD Flow
1. Code pushed → GitHub triggers Jenkins.
2. Jenkins builds → Docker image.
3. Image pushed → to registry (Docker Hub / GCP Artifact Registry).
4. Deployment applied → automatically to Kubernetes cluster.
5. Monitoring & notifications → using Jenkins plugins or tools like Dynatrace/Prometheus.
