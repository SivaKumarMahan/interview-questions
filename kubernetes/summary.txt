4. Advanced Kubernetes – Quick Notes 📝

--> StatefulSets vs Deployments: StatefulSets = stateful apps (stable Pod ID + storage); Deployments = stateless apps.

--> Service Mesh: Manages secure, reliable service-to-service communication with traffic control and observability (e.g., Istio).

--> Cluster Security: RBAC, Network Policies, encrypted Secrets, TLS, Pod security policies, audits.

--> Taints & Tolerations: Taints repel Pods from nodes; tolerations allow Pods to run on tainted nodes.

--> Sidecar Containers: Helper containers in a Pod for logging, monitoring, or proxies.

--> Common Pod Errors: ImagePullBackOff (fix image/registry), CrashLoopBackOff (check logs/resources), Pending (scale cluster/fix requests).

--> Mutating Admission Webhook: Modifies resources (e.g., auto-inject sidecars) before saving in etcd.

--> Zero-Downtime Deployment: Use rolling updates with readiness probes, or blue-green/canary strategies.

--> Custom Resource Definitions (CRDs): Extend Kubernetes with custom resources for domain-specific apps.

--> Operators: Automate app lifecycle (deploy, scale, backup) using CRDs + controllers.

5. --> Kubernetes → Open-source container orchestration platform for automating deployment, scaling, and management of containerized apps.

--> Pod → Smallest deployable unit in Kubernetes, a wrapper around one or more containers sharing network and storage.

--> Deployment → Controller that manages Pods and ReplicaSets, supports scaling, rolling updates, and rollbacks.

--> Service → Provides stable networking (IP/DNS) and load balancing for Pods whose IPs change dynamically.
--> Service Types →
1. ClusterIP (internal only)
2. NodePort (exposes via Node IP:Port)
3. LoadBalancer (cloud LB for external access)
4. ExternalName (maps to external DNS)
5. Headless (direct Pod-to-Pod).

--> ConfigMaps & Secrets → Store configuration and sensitive data separately from code; Secrets are base64-encoded.

--> Namespaces → Logical partitions in a cluster for isolation, multi-tenancy, and resource management.

--> Labels & Selectors → Labels = key-value identifiers; Selectors = queries to filter/manage resources based on labels.

--> PV & PVC → PV = actual storage resource, PVC = user’s request for storage; used to persist data beyond Pod lifecycle.

6. ■ What are Persistent Volumes (PVs) and Persistent Volume Claims (PVCs)? 
--> PV = storage resource, 
--> PVC = request for storage. 
--> Decouples storage from Pods, ensures data persistence. 
■ What is Kubernetes networking, and how does it work? 
--> Each Pod gets a unique IP, all Pods can talk without NAT, Services provide stable DNS/IP. Implemented via CNI plugins. 
■ What is Role-Based Access Control (RBAC) in Kubernetes? 
--> Security mechanism that controls access to resources using Roles/ClusterRoles and RoleBindings. 
■ How does Kubernetes autoscaling work? 
--> HPA scales Pods based on metrics, 
--> VPA adjusts resource requests, 
--> Cluster Autoscaler adds/removes nodes. 
■ How do you debug Kubernetes Pods? 
--> Use kubectl describe, logs, exec, and get events to inspect issues. 
■ How do you perform rolling updates and rollbacks in Kubernetes? 
--> Rolling update upgrades Pods gradually (zero downtime), 
--> rollback restores previous version using kubectl rollout. 
■ What is an Ingress in Kubernetes, and how does it work? 
--> API object managing HTTP/HTTPS external traffic using rules and Ingress Controllers. 
■ How does Kubernetes handle resource limits and requests? 
--> Requests = guaranteed resources, 
--> Limits = max allowed; 
exceeding memory kills Pod, CPU just throttles. 
■ What happens if a Pod resource needs to grow beyond the assigned limits? 
--> CPU over limit → throttling; Memory over limit → OOMKilled. 
■ What are init containers, and when should you use them? 
--> Special containers that run before main containers to set up environment/configs/dependencies. 
■ How does Kubernetes handle Pod disruptions and high availability? 
--> Uses ReplicaSets, PodDisruptionBudgets, and rescheduling on healthy nodes for HA.

7. Inside a Pod, all containers share:

1. Network → Same IP, same localhost.
2. Storage → Shared volumes for data exchange.
3. Env Vars / Metadata → Pod-level environment variables & configs.
4. (Optional) IPC → Can communicate using system signals.
👉 This makes containers inside a Pod work like they are on the same machine, tightly coupled.

In easy way to remember:
🏠 Pod = House
A Pod is like a house where multiple roommates (containers) live together.
👥 Containers = Roommates
Each container is a roommate with its own work (web app, logging, monitoring, etc.).
🌐 Shared Network = Same Wi-Fi
All roommates share the same Wi-Fi (IP address).
They talk to each other using localhost (like chatting inside the house).
📂 Shared Storage = Common Fridge/Bookshelf
There’s a common fridge or bookshelf (Volume).
Whatever one puts in, the others can also use.
📝 Shared Env Vars = House Rules
Rules (like “no loud music after 10 PM” or “APP_ENV=production”) apply to all roommates equally.
🛎 Optional IPC = Knocking on Doors
Roommates can also signal each other (like knocking or passing notes).
👉 So, containers in the same Pod = roommates in one house, sharing Wi-Fi, storage, and rules, but each still does their own job.

8. Question 2: Kubernetes Troubleshooting
Your team deployed a Spring Boot microservice on GKE, but the pod is stuck in CrashLoopBackOff.
As a DevOps engineer,
How would you troubleshoot this issue?
What commands or tools would you use to debug it?

Answer: If a pod is stuck in CrashLoopBackOff, I’d follow these steps:
🔍 1. Check Pod Status and Events
kubectl get pods
kubectl describe pod <pod-name>

--> Look for reasons in the Events section: missing images, failed mounts, liveness probe errors, etc.

🔍 2. Check Logs
kubectl logs <pod-name> --previous

--> --previous shows logs from the previous crashed container.
--> This helps identify application-level errors (e.g., DB connection failure, wrong configs).

🔍 3. Verify Configuration
--> Check image name and tag (wrong image causes crashes).
--> Validate ConfigMaps/Secrets:

kubectl get configmap
kubectl get secret

🔍 4. Check Health Probes
--> Misconfigured liveness/readiness probes often cause restarts.
--> Verify them in the Deployment manifest:

livenessProbe:
 httpGet:
 path: /health
 port: 8080
 initialDelaySeconds: 30

🔍 5. Test Locally
--> Run the same Docker image locally to see if it crashes outside Kubernetes:

docker run -it <image-name>

🔍 6. Restart or Roll Back
--> If a quick fix exists, restart pods:
kubectl rollout restart deployment <deployment-name>
--> If not, rollback to a previous working version:
kubectl rollout undo deployment <deployment-name>

🔍 7. Check Cluster Resources
--> Sometimes crashes are due to out-of-memory (OOM) or resource limits.
kubectl top pod
kubectl describe node <node-name>

🔍 8. Root Cause Resolution
--> Once root cause is found (e.g., bad config, missing dependency, low memory), fix the Deployment or ConfigMap and re-deploy.

💡 What to Say in Interview:
“I first check pod status with kubectl describe pod and review logs with kubectl logs --previous. Then I verify configuration, secrets, and health probes. If necessary, I test the image locally and restart or roll back. I also check node resource usage with kubectl top. This structured approach helps isolate whether the issue is application-level, configuration, or resource-related.”

9. Question: What is Kubernetes Manifests?
Answer: A Kubernetes manifest is a YAML file that defines the desired state of your application or infrastructure in a Kubernetes cluster.
 It tells Kubernetes:
“I want 3 replicas of this app running, with these environment variables, secrets, and resource limits.”
Common Manifest Types:
1. Deployment: Runs your app containers.
2. Service: Exposes your app internally or externally.
3. ConfigMap/Secret: Stores configuration and secrets.
4. Ingress: Routes traffic from the internet.
5. HPA (Horizontal Pod Autoscaler): Scales pods automatically.
