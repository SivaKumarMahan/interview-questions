1. What is GitLab CI/CD?
Answer: GitLab CI/CD is GitLab's built-in automation platform for building, testing, scanning, packaging, and deploying code. Pipelines are defined in `.gitlab-ci.yml` and run on GitLab runners.

2. What are stages, jobs, and runners in GitLab CI?
Answer: Stages define pipeline order, jobs define the actual work, and runners execute jobs. A runner can be shared, group-level, project-specific, shell-based, Docker-based, or Kubernetes-based.

3. How do you define a simple GitLab CI pipeline?
Answer: Create `.gitlab-ci.yml`, define stages such as build, test, scan, and deploy, then define jobs under each stage. Each job uses a script and can specify image, cache, artifacts, variables, and rules.

4. What is the difference between `only/except` and `rules`?
Answer: `only/except` is the older way to control when jobs run. `rules` is more flexible and can evaluate branch names, file changes, variables, merge request context, and manual conditions.

5. How do artifacts and cache differ in GitLab CI?
Answer: Artifacts are job outputs passed to later jobs or downloaded after the pipeline. Cache stores reusable dependencies between pipeline runs to speed up builds, such as npm or Maven caches.

6. How do you manage secrets in GitLab CI?
Answer: Use protected and masked CI/CD variables, environment-scoped variables, external secret managers, and protected branches/tags. Avoid printing secrets in logs and restrict who can edit pipeline configuration.

7. How do you deploy to Kubernetes from GitLab CI?
Answer: Build and push the container image, authenticate to the Kubernetes cluster with a protected variable or GitLab agent, deploy using Helm or kubectl, wait for rollout status, and run post-deployment checks.

8. What are manual jobs and environments in GitLab CI?
Answer: Manual jobs require a user to start them, commonly for production deployments. Environments represent targets like dev, staging, and production, and can track deployments, rollback links, and approval workflows.

9. How do you optimize GitLab CI pipeline speed?
Answer: Use cache, dependency proxy, smaller images, parallel jobs, `needs`, rules to skip unnecessary jobs, runner autoscaling, and split long test suites into parallel shards.

10. How do you troubleshoot GitLab CI failures?
Answer: Review the failed job log, runner status, Docker image availability, variables, permissions, artifacts, cache, branch rules, and recent `.gitlab-ci.yml` changes. Re-run failed jobs after fixing the root cause.
