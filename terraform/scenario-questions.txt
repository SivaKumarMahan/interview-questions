1. How do you manage multiple Terraform workspaces across environments?
Answer: Use terraform workspace new/select → Or create separate state files with backend configs → Automate via pipelines.

Detailed interview approach:
I keep reusable modules small, versioned, documented, and free of environment credentials/names. They expose validated inputs and stable outputs, apply secure defaults, and include examples and automated format, validation, security, and integration tests. Environment root modules pin a released version and use separate backends, variables, identities, and approvals for Dev/QA/Prod. For a breaking change I release a major version with a migration guide and test it in lower environments before promotion. Ownership and code review prevent teams from copying and silently modifying modules; controlled extension points handle legitimate differences.

2. How do you prevent accidental deletion of critical Terraform resources?
Answer: Use prevent_destroy = true in resource block → Enable approval workflows before apply.

Detailed interview approach:
I do not apply a replacement or deletion until I know which changed argument caused it and whether the resource contains data or serves traffic. I save/review the plan, check provider documentation and recent state/code changes, and verify backups and recovery. Guards include `prevent_destroy`, provider deletion protection, policy checks that reject destructive plans, least-privilege production credentials, and approval gates. If a destructive apply has already started, I stop new runs, assess real resources and state, restore service/data from replicas or backups, import surviving objects where needed, and review a recovery plan. I fix code and validate both infrastructure and application before removing any temporary protection.

3. How do you handle Terraform state when migrating infra across clouds?
Answer: Import existing resources into Terraform, migrate state files step by step, update backend config, and validate before applying.
Mini-case: We migrated from GCP to Azure; using terraform import preserved resources without downtime.

Detailed interview approach:
I stop concurrent jobs and confirm the exact backend, workspace/state key, and lock owner. I preserve `terraform state pull`, the saved plan, backend version, and cloud audit evidence before any state operation. For a stale lock I prove no apply or provider operation is running, then use the backend's supported unlock or `terraform force-unlock <id>`; I never delete it merely because a job is waiting. For loss/corruption I restore backend version history first, or rebuild state by writing matching code and importing real resources. A full plan must show no surprise before apply. Encryption, versioning, locking, least privilege, isolated states, and tested restoration prevent recurrence.

4. How do you debug Terraform remote backend locking issues?
Answer: Check lock status in backend (e.g., DynamoDB/GCS), remove stale lock after validation, and avoid concurrent applies. Mini-case: A crashed pipeline left a lock in GCS; after manual removal, we added timeouts to auto-release stale locks.

Detailed interview approach:
I read the lock record and identify operation, owner, timestamp, state key, and CI run. I confirm through the pipeline and cloud activity logs that no Terraform/provider process is still changing resources. If it is active, I wait or stop it safely; if it is stale after a crash, I use the backend-supported unlock or `terraform force-unlock <lock-id>` for that exact state. I never delete a lock table/object blindly. Then I run a full refresh/plan to detect partial operations and reconcile any created-but-untracked resource. Serialized pipeline deployments, reasonable lock timeouts, isolated state boundaries, backend monitoring, and run cancellation handling reduce lock contention and abandoned locks.

5. How do you prevent drift between Terraform code and manually modified resources?
Answer: Run regular drift detection (terraform plan), enforce GitOps (disallow manual changes), and monitor audit logs for manual edits. Mini-case: A manual firewall rule was added; next pipeline run flagged drift and auto corrected it to match code.

Detailed interview approach:
I run a read-only `terraform plan -detailed-exitcode`, preserve the diff, and use cloud activity logs to identify who changed what and why. I decide with the owner whether the manual value is desired. If yes, I update reviewed Terraform code or import the legitimate object; if not, an approved apply restores the declared state. I do not hide broad fields with `ignore_changes` or auto-revert an emergency fix without review. After reconciliation I require a clean plan and application check. Scheduled drift plans, restricted console write access, policy-as-code, and a break-glass process that requires later reconciliation keep code authoritative.

11. How do you ensure Terraform changes are peer-reviewed before apply?
Answer: Use Git PR workflows → Automate terraform plan in CI → Require approval before merge.

Detailed interview approach:
The pull-request pipeline runs `terraform fmt -check`, `init`, `validate`, lint/security/policy tests, and `terraform plan -out=tfplan` with short-lived least-privilege credentials. After apply I run infrastructure and application smoke checks. On failure the job stops for state/cloud reconciliation; it never blindly destroys or automatically retries a partial production apply.

13. How do you troubleshoot Terraform dependency cycle error?
Answer: Identify cyclic references → Break into modules → Use depends_on explicitly.

Detailed interview approach:
I stop automatic retries, capture the exact resource address/provider error, saved plan, state version, and cloud activity log. I do not hide broad fields with `ignore_changes` or auto-revert an emergency fix without review. After reconciliation I require a clean plan and application check. Scheduled drift plans, restricted console write access, policy-as-code, and a break-glass process that requires later reconciliation keep code authoritative.

41. How do you optimize Terraform execution time?
Answer: • Use smaller state files (split projects).
• Run in parallel with -parallelism.
• Use modules to reduce duplication.

Detailed interview approach:
I measure whether time is spent downloading providers, refreshing many resources/data sources, waiting on API throttling, or following unnecessary graph dependencies. I split unrelated lifecycle domains into smaller locked states, narrow broad data sources, remove artificial `depends_on`, cache trusted provider downloads in CI, and run independent state plans in parallel within provider rate limits. I avoid making `-target` the routine optimization because it can produce an incomplete plan. I compare timings and API errors after each change and keep a scheduled full drift plan so faster pull-request feedback does not hide infrastructure differences.

42. What if a Terraform apply fails halfway?
Answer: Terraform normally records successfully completed resource changes in state even if a later operation fails. I stop automatic retries, read the exact provider error, inspect the state and real cloud resources, and check activity logs, permissions, quotas, networking, and provider status. I do not delete resources or edit state blindly.

If the provider created a resource but state did not record it, I write matching configuration and import it. If state contains an object that no longer exists, I confirm the intended outcome before using state commands. After correcting the root cause, I run a full `terraform plan`, review all proposed changes, apply the approved plan, and validate the infrastructure and application. For state reconciliation I use a normal plan or an intentional `-refresh-only` workflow rather than relying on the deprecated standalone `terraform refresh` command.

Detailed interview approach:
I stop automatic retries, capture the exact resource address/provider error, saved plan, state version, and cloud activity log. I check credentials, quota/rate limits, API status, network, immutable arguments, dependency ordering, and provider version. Then I compare state with the real object: if the API created it without a state update I import it; if it is recorded but absent I decide whether to recreate or remove the state entry. I fix the cause, use backoff for API throttling, run a new full plan, and review all changes before apply. State commands and `TF_LOG` are controlled because both can expose or damage sensitive state.

43. How do you implement rollback in Terraform?
Answer: Terraform does not provide an application-style rollback command. I revert the configuration to a known-good Git commit, run a new plan, review whether the provider can reverse each change safely, and apply that new plan. Some changes, such as data deletion, database migration, or an immutable-resource replacement, require a service-specific restore or failback plan.

Backend state versions are for state disaster recovery, not for rolling infrastructure back. Restoring an old state while the real infrastructure remains changed can make Terraform believe incorrect information and cause destructive actions. I restore state only when state itself is lost or corrupted, after backing up the current state and reconciling it carefully with actual resources.

Detailed interview approach:
I do not apply a replacement or deletion until I know which changed argument caused it and whether the resource contains data or serves traffic. I save/review the plan, check provider documentation and recent state/code changes, and verify backups and recovery. Guards include `prevent_destroy`, provider deletion protection, policy checks that reject destructive plans, least-privilege production credentials, and approval gates. If a destructive apply has already started, I stop new runs, assess real resources and state, restore service/data from replicas or backups, import surviving objects where needed, and review a recovery plan. I fix code and validate both infrastructure and application before removing any temporary protection.

44. How do you manage Terraform modules for reusability?
Answer: Create modules for common components (VPC, VM, AKS/GKE, IAM) → Store them in Git → Call modules in different projects with version control.

Detailed interview approach:
I keep reusable modules small, versioned, documented, and free of environment credentials/names. They expose validated inputs and stable outputs, apply secure defaults, and include examples and automated format, validation, security, and integration tests. Environment root modules pin a released version and use separate backends, variables, identities, and approvals for Dev/QA/Prod. For a breaking change I release a major version with a migration guide and test it in lower environments before promotion. Ownership and code review prevent teams from copying and silently modifying modules; controlled extension points handle legitimate differences.

45. What if two team members run Terraform apply at the same time?
Answer: Use remote backend with state locking (like Azure Blob with locking or GCS with locking) → This prevents conflicts.

Detailed interview approach:
I stop concurrent jobs and confirm the exact backend, workspace/state key, and lock owner. I preserve `terraform state pull`, the saved plan, backend version, and cloud audit evidence before any state operation. For a stale lock I prove no apply or provider operation is running, then use the backend's supported unlock or `terraform force-unlock <id>`; I never delete it merely because a job is waiting. For loss/corruption I restore backend version history first, or rebuild state by writing matching code and importing real resources. A full plan must show no surprise before apply. Encryption, versioning, locking, least privilege, isolated states, and tested restoration prevent recurrence.

Store state in backend.

Detailed interview approach:
